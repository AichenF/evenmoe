同一条 SGLang 推理时间线，MLB 应该出现在哪里？

“当前”和“目标”使用完全相同的 L1 阶段和步骤；第三栏单独展开开启 UltraEP 后复用 现有 EPLBManager 的完整 rebalance 时间线。点击图面可依次切换三个视图。 “当前”区分 SGLang main 已有的 EPLB / LPLB / Waterfill 与 MLB 仓库中的 POC runtime； “目标”是尚未实现的建议设计：SGLang 只持有一个 SGLangMoELoadBalancer Adapter/Façade，由它调用框架无关的 MoELoadBalancer Orchestrator。 UltraEP 栏严格区分三方边界：SGLang 拥有生命周期和权重，MLB 只计算 placement/reroute， UltraEP 只按外部 placement 提供 NVSHMEM weight-sync 通信。

图二 · 目标设计

目标设计：SGLang 只选择一个算法表达式；MLB 组装统一 L2 Pipeline

SGLang 仍然决定何时初始化、前向推理、重新计算布局和搬权重；MLB 只在这些固定位置 被调用。ModelRunner 只持有一个框架无关的 MoELoadBalancer； SGLang Adapter 保持无状态，只负责把 live metadata 和运行期统计翻译成 MLB 请求。 EPLB 的 Step 1–6、8–15 和 Missing-weight recovery 直接复用 reviewed restored 流程； Step 7 的生命周期位置保持不变，但执行者改为“前置 Adapter → MLB Orchestrator → 后置 Adapter”。 --moe-load-balancer-algorithm 接受单算法或 + 组合； 解析、校验、能力推导和算法实例化全部由 MLB 完成。static、 dynamic、实验性的 fake、lplb 与 waterfill 都由 MLB 拥有；SGLang 只保留兼容不同 TopK/硬件后端的调用点。 L2 始终从 SGLang 已生效的 metadata 读取 placement；初始权重加载或 placement 更新完成后，SGLang 用 committed snapshot 调用一次 on_placement_committed()，不维护 placement version 或 snapshot cache。

SGLang threshold gate · 通过后才调用 MLB SGLang EPLBManager 维护 every-N cadence；到周期后执行 dump、physical→logical、ALL-REDUCE(SUM) 和 reset，并判断 utilization threshold。未跳过时，Adapter 才把最终 payload 翻译成 PlacementStats，由 MLB EPLB Policy 运行 placement 算法。
L1 生成 plan 后不能马上切换 L2 Step 12 只得到 candidate PlacementPlan。Step 13、Step 14 和 missing-weight recovery 全部由 SGLang 完成；期间 L2 继续使用旧 PlacementSnapshot。全部成功后，SGLang 才从真实 metadata 构造新 snapshot，并对已更新 layer 调用 MLB on_placement_committed()；MLB 根据当前 pipeline 自动通知需要 placement 派生状态的 policy，SGLang 不出现 LPLB 分支。下一轮 forward 仍直接从同一份 live committed metadata 构造 request snapshot。两侧都不缓存 placement snapshot；MLB 不比较 Tensor、不管理 placement version；SGLang 也不承担 LPLB CUDA Graph recapture。
待解决 · LPLB CUDA Graph shape stability 当前 LPLB 按 single-copy 与 replicated logical expert 构造紧凑 LP 矩阵。同样的每-rank physical slot 数量并不能保证矩阵形状不变：EPLB 可能把副本分布从 [2,2,1,1] 改成 [3,1,1,1]。shape 相同时 MLB 可以原位更新已捕获 graph 引用的 tensor；shape 改变时，现有紧凑表示尚不能保证旧 graph 正确读取新 placement。本次删除 SGLang recapture 补丁，后续应在 MLB 内将 LPLB 改成固定容量、固定地址的 graph-stable 状态，而不是让框架感知算法内部矩阵形状。
fake 是 MLB 的实验策略，不是 SGLang 特例 fake 包含两个算法步骤：TopK 前生成 uniform random router stimulus，以及 TopK 后像 dynamic 一样随机选择 committed replica。两步都由 MLB 实现；SGLang 只在原有 TopK 生命周期位置调用，因此 fused shared expert、HashTopK 和 NPU 的框架兼容逻辑不进入 MLB。
一个参数选择单算法或组合 static、dynamic、fake、lplb、waterfill 或 lplb+waterfill 都经 --moe-load-balancer-algorithm 进入 MLB。裸 waterfill 由 MLB 规范化成 static+waterfill；原来的两个 selector 和 dynamic Waterfill 环境变量已删除，运行路径只有这一处选择入口。

ONE MLB · COMM BACKEND = UltraEP
SGLang · 生命周期与权重唯一所有者 拥有 expert tensors、FP8 scales、EPLB cadence、active metadata、DeepEP dispatch 和真正的 GEMM 执行；先搬权重，后提交新布局。
MLB · 纯算法 L3 根据 load/topology 输出 placement；L2 根据 placement 把 logical TopK 改成 physical TopK。绝不接收权重、scale 或通信指针。
UltraEP · 纯通信后端 只新增一个 weight_sync_from_placement() API：接收外部 maps，复用既有 weight_sync() 搬运 payload；不收集 load，不决定 cadence，不计算 placement。
