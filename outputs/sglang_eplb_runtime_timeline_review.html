2. 最清晰的三层边界

紫色：SGLang 原生能力 蓝色：SGLang Adapter 绿色：MLB Core / Policy

留在 SGLang

  • 在 TopK、DeepEP、MORI 等真正执行位置采到原始数据。
  • ModelRunner 决定何时初始化、forward 何时结束、模型何时销毁。
  • 持有模型参数、权重 loader、DRAM backup、磁盘 loader。
  • SGLang EPLBManager 决定何时应用候选 plan，并调用自己的 Updater 执行同 GPU copy、NCCL P2P、故障恢复和 metadata 更新。
  • 保存当前真正生效的 placement，并在成功更新后推进 SGLang 自己的 placement version。
  • 在下一次 TopK 中把逻辑 expert id 映射到已生效的物理副本。

原因：这些代码直接依赖 SGLang 的模型、backend、process group 和执行顺序。

放在一个 SGLang Adapter

  • 把 SGLang 的采样结果整理成普通 Tensor。
  • 使用 SGLang 的 EP group 做 all-reduce / broadcast。
  • 从 server_args、model config、metadata 提取普通标量。
  • 构造 MLB 的 PlacementRequest / RoutingRequest。
  • 提供 plan / decision 与 SGLang 数据结构之间的纯转换；转换结果返回给 SGLang 调用方。
  • 从 SGLang 当前 metadata/version 构造只读 PlacementSnapshot，供 MLB 的 L1/L2 使用。

它只与框架绑定，不与 EPLB、LPLB、Waterfill 中任一算法绑定。

放在 MLB Core / Policy

  • 收到 SGLang recorder 已完成汇总的 PlacementStats 后，决定是否运行 L1 rebalance。
  • 运行 DeepSeek EPLB 等 L1 planner，输出候选布局。
  • 定义框架中立的 PlacementRequest、PlacementPlan 和 PlacementSnapshot 接口。
  • 让 L2 从 Adapter 提供的 SGLang 当前 snapshot 读取已经生效的 L1 布局。
  • 按配置执行 LPLB → Waterfill 等有顺序的组合。

它不 import SGLang，不知道 ModelRunner、NCCL group 或真实权重对象。

一句话：SGLang 产生事实、控制生命周期并修改模型；Adapter 翻译数据与结果； MLB 根据框架中立的数据作决定。
“执行框架动作”不等于 Adapter 接管框架生命周期： Adapter 可以做普通数据转换、调用 EP collective、把最终 routing decision 写成 TopK/DeepEP 所需格式； 但“何时搬模型权重、调用哪个 Updater、失败后怎样恢复”必须由 SGLang EPLBManager 主动控制。 调用方向应是 SGLang Manager → Adapter 转换 → SGLang Updater，而不是 Adapter → SGLang Updater。
为什么 placement 生效状态留在 SGLang： 判断标准不是这段代码只有几行还是很多行，而是谁能证明状态真的生效。 只有 SGLang 知道真实权重是否已经搬完、执行 metadata 是否已经更新； 因此 MLB 负责“算出候选方案”，SGLang 负责“保存当前事实”，Adapter 负责“把事实翻译给 MLB 看”。

3. 官方 SGLang main 的 EPLB 全景

以下只描述官方 SGLang main 在 c6a6200a1a778a799ba61c395ac292317f01ebc9 的当前实现， 不混入“以后应该放到 Adapter 或 MLB”的设计建议。官方实现主要集中在 python/sglang/srt/eplb/，但真正的闭环横跨配置、ModelRunner、TopK、 token dispatcher、FusedMoE weight loader、Elastic EP 和 HTTP 控制入口。

重新校验后的结论：原表列出的“初始化 → 记录 → 汇总 → 判断 → 计算 → 搬权重 → 下次 forward”主线基本正确，但不够全面，而且 “建议归属”一列把目标设计混进了官方现状。下面改成 官方正常主线和官方特殊/辅助分支两部分。

10. 本轮 Review 的核心问题

Blocker / Major #8 · Planner 结果在权重 apply 前就 publish

当前 compute_placement() 在返回 candidate map 前就执行 self._provider.update_with(plan)。如果 L2 此时读取 provider，它会按“新布局”路由， 但 SGLang 的真实权重可能还没搬、甚至搬运失败。

建议：plan() 只返回 candidate；SGLang EPLBManager 校验 base version， 调用自己的 apply()。删除 MLB provider 的提前 update，L2 通过 SGLangPlacementAdapter 只读地取得 SGLang 当前真实 placement。

Major #9 · 统计张量的通信语义自相矛盾

SGLangStatsBridge 说输入已经跨 EP all-reduce； SGLangEPLBRuntime.drain_stats() 又要求 caller 对结果 all-reduce。 官方 SGLang 实际是在 physical→logical 转换后、dump 时 all-reduce logical count。

建议：SGLang 生产路径只保留 SGLangStatsCollector： 官方 dump_record(output_mode="object") 负责 physical→logical 和官方 distributed all-reduce，Adapter 只把已是全局结果的 dump 转成 PlacementStats。不要再对它重复通信。

Major #10 · 算法支持面与官方 SGLang 不一致

MLB 保留了 deepseek_vec 和 elasticity_aware 的公开枚举， 实现却是 stub。尤其 Elastic EP 会由官方配置自动选到未实现路径。

建议：要么本 PR 完整迁入并加等价测试；要么暂时从公开 capability 中移除并在 Adapter 初始化时 fail fast， 不要等第一次 rebalance 才报错。

Major #2/#3/#6 · runtime 形状仍是“框架 × 算法”

当前有 SGLangEPLBRuntime、WaterfillRuntime、 LPCFRuntime，并且 EPLB 还有进程级 default registry。 继续这样扩展会把 M 个框架 × N 个算法变成 M×N 个 runtime。

建议：一个框架只有一个 Adapter；一个模型/engine 只有一个 MoELoadBalancer 实例。 算法是实例内部 policy，不拥有框架 lifecycle。

Major #1/#4 · 两套 stats 路径和两个 placement source

一条路径用 SGLangStatsCollector 包装原生 recorder，另一条用 SGLangStatsBridge 替换原生 buffer；同时又有 MLB EPLBPlacementProvider 和读取 SGLang metadata 的 SGLangPlacementAdapter。这会形成双写和“谁是真值”的问题。

建议：生产 stats 路径只保留包装官方 recorder 的 SGLangStatsCollector； placement 侧只保留一份真值。SGLang metadata/version 是唯一真值； SGLangPlacementAdapter 只把它转换成框架中立 snapshot，MLB 不再维护副本。 version 由 SGLang 在 apply 成功后推进。

Major #11 · SGLang 应传一个统一 Request class

当前 compute_placement() 对外要求分别传 logical_count、物理专家数、每 GPU 专家数、group 数、node 数、算法名和 active ranks，随后函数内部才把它们重新包装成 PlacementRequest。 这会让参数组装和默认值分散到多个 SGLang 调用位置。

建议：唯一的 SGLang Adapter 一次性构造框架中立、带类型的 现有 PlacementRequest(stats, policy, current)，layout 标量按当前合约放在 PlacementPolicyConfig.metadata，再传给目标顶层 MoELoadBalancer.plan_placement(request)（目标概念名，当前尚未实现）。Request 中不能携带 ServerArgs、ModelRunner、process group 或模型对象；L2 同样统一使用 RoutingRequest。

Major #12 · L2 仍是每个算法一个 SGLang runtime，无法清晰组合

当前 LPCFRuntime 和 WaterfillRuntime 各自读取 ForwardBatch、统计、通信、构造 request、调用 router 并 materialize。 同时 RoutingRequest.policy.name 一次只能选择一个 policy； 所以“先 LPCF、再 Waterfill”没有统一的中间状态和调度者。

建议：每个模型/engine 只创建一个 L2Runtime。LPCF、Waterfill 注册成其内部有顺序的 policy pipeline，共享一个 routing context； SGLang 数据准备、必要 collective 和最终写回只经过同一个 Adapter。

11. 建议的最终设计：M + N，而不是 M × N

这里必须分成两条互不混淆的路径： L1 EPLB 是每 N 次 forward 才运行的慢路径，负责改变专家副本布局； L2 是每次 forward / TopK 后运行的快路径，负责在当前已生效布局上路由 token。 L2 不能被画成“一次周期性 EPLB”的最后一步。

SGLang 只初始化两个对象

self.moe_load_balancer = MoELoadBalancer(config)
self.moe_lb_adapter = SGLangAdapter(
    balancer=self.moe_load_balancer,
    ep_group=self.moe_ep_group,
    placement_reader=self.read_expert_location,
)

对象由 ModelRunner/engine 持有，不放进 MLB 全局 registry；Adapter 没有 apply_placement / Updater callback。SGLang EPLBManager 自己应用 L1 plan。

一个总 Orchestrator，只持有一个 L2Runtime

MoELoadBalancer
├── l1_controller
│   └── placement policies
└── l2_runtime              # 每个 model/engine 只有一个
    ├── policy registry
    ├── per-layer neutral state
    └── pipeline: [lpcf, waterfill]

LPCFRouter、WaterfillRouter 是 L2Runtime 内的 policy， 不是各自拥有 SGLang lifecycle 的 runtime。一个 runtime 可以用 layer_id → state 保存多层状态，不代表每层、每算法再创建 runtime。

11.1 当前 L2 为什么不对

当前源码：每个算法各自一套 runtime

SGLang → LPCFRuntime
        ├── 统计 / collective
        ├── 构造 RoutingRequest
        ├── LPCFL2Router
        └── materialize TopK

SGLang → WaterfillRuntime
        ├── 统计 / collective
        ├── 构造 RoutingRequest
        ├── WaterfillL2Router
        └── materialize TopK

两个 runtime 都读取 ForwardBatch、管理 buffer、做 SGLang 通信并写回 StandardTopKOutput。新增算法会继续复制框架 glue，形成 M×N。

目标：一次进入、内部组合、一次写回

SGLang TopK
  ↓
one SGLangAdapter.prepare_routing()
  ↓ one RoutingRequest / RoutingContext
one MoELoadBalancer.l2_runtime.route()
  ├── LPCF policy
  └── Waterfill policy
  ↓ one final RoutingDecision
one SGLangAdapter.materialize()
  ↓
SGLang TopK / DeepEP

Adapter 只和 SGLang 绑定；L2Runtime 只和 MLB Core 绑定；算法 policy 不读取 ForwardBatch、不持有 EP group，也不生成 SGLang 对象。

目标 L2 API 还需要补一层： 当前 RoutingRequest.policy.name 一次只能表达一个算法。目标应由 L2Runtime 接收有顺序的 pipeline 配置，并维护一个共享 RoutingContext：前一 policy 的结果成为后一 policy 的输入。 例如 LPCF 先选择 routed expert 的物理副本，Waterfill 再基于该结果安排 shared expert。
多算法之间的数据依赖也要由这一个 runtime 处理： Waterfill 需要统计 LPCF 选完之后的 physical ids 落到各 rank 的负载， 所以这份数据不能全部在 pipeline 开始前准备。正确流程是 L2Runtime 先运行 LPCF， 再让同一个 Adapter 对中间结果做一次必要的统计/collective，然后继续 Waterfill； 这仍是一次 route_tokens()、一个 L2Runtime，不是再创建 WaterfillRuntime。

11.3 目标 Timeline B：L2 每次 forward 的统一快路径

SGLang TopKL2-1 · 产生本次 logical topk

SGLang 把 topk_ids、weights、forward stage 和 token 有效范围交给唯一 Adapter hook。

一次 adapter.route_tokens(...)
一个 SGLang AdapterL2-2 · 准备公共输入与框架能力

Adapter 读取当前 SGLang placement snapshot，整理 logical topk、stage 和 token 范围， 并向 L2Runtime 提供统一的“统计/EP 汇总”能力。尚未产生的中间数据不会在这里提前猜。

一个 framework-neutral routing context
唯一 L2RuntimeL2-3 · 解析有顺序的 policy pipeline

L2Runtime 根据统一配置取得 [lpcf, waterfill]，负责 stage gating、 policy 调度、共享中间结果和错误边界；不是根据一个 name 创建某个算法 runtime。

context：logical ids + current placement
LPCF policyL2-4 · 先选择 routed expert 的物理副本

LPCF 只读取普通 tensor/snapshot，输出 physical routed ids，并把结果写入共享 context。

此时才有 LPCF 选择后的 physical ids
同一个 SGLang AdapterL2-5 · 按下一 policy 的需求补充派生数据

L2Runtime 通过统一接口让 Adapter 统计这些 physical ids 的 routed-rank load； dynamic Waterfill 需要时只做一次 EP collective，static 模式则不做。结果放回同一 context。

context：physical routed ids + routed rank load
Waterfill policyL2-6 · 再安排 shared expert

Waterfill 消费前一阶段结果和刚补充的 load，选择 shared-expert rank；算法本身不读取 SGLang 或持有通信组。

一个 final RoutingDecision
同一个 SGLang AdapterL2-7 · 一次 materialize

Adapter 把最终 physical ids、weights 和 shared-expert 选择一次性转成 SGLang TopK/DeepEP layout。

返回 SGLang forward
SGLangL2-8 · 按最终 layout dispatch token

DeepEP/其他 backend 继续负责真实 dispatch；MLB L2 不持有通信组或 SGLang 对象。

这样为什么是 M+N： 新增框架只实现一个框架 Adapter；新增算法只实现一个 Core policy。 每个模型/engine 只有一个顶层 MoELoadBalancer 和一个 L2Runtime，不需要为 “SGLang×LPCF”、“SGLang×Waterfill”、“vLLM×LPCF” 分别再造 runtime。
