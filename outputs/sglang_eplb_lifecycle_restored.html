步骤 2：外层 initialize 内部调用 init_by_eplb ModelRunner.initialize() → maybe_init_expert_location_metadata() → compute_initial_expert_location_metadata() → init_by_eplb() 都属于 SGLang Glue。步骤 3 的 metadata 仍由 SGLang 创建；只有其中“普通输入算 maps”的嵌套调用进入当前 MLB runtime/policy。当前 runtime 还组合了 Recorder、Planner、skip 配置和全局 Registry。
Recording 入口：StatsBridge SGLang 的 TopK/DeepEP 等 backend 在每一层产生 physical count；这些 hook 先写本次 forward 的临时 gatherer。只有所有 MoE layer 完成，forward-end 才把完整 tensor 交给 SGLangStatsBridge.append_per_forward()，再 push 给 MLB Recorder。它不是每记录一层就判断 rebalance。
数据保存：EPLBRecorder 在 MLB 每个完整 forward 只复制一份 [layer, physical expert] tensor 到 MLB 的 deque，只保留最近 N 次；collect() 求和、physical→logical，并清空窗口。Recorder 只保存和整理数据，不做 placement 决策，因此用中性灰色，不归入 Policy。
另一条 Recording 路径仍存在 SGLangStatsCollector 不使用 MLB buffer，而是读取 SGLang 原生 recorder 的 dump。它与 StatsBridge 是两套互斥设计，目前代码没有选定唯一生产路径，all-reduce 语义也不一致。
第 11 步当前也被拆开 “每 N 次 forward”由 SGLang EPLBManager 触发，这一点与目标一致；当前触发后进入算法专用 SGLangEPLBRuntime，其中混合了 drain 和 threshold/skip。目标边界只保留 Adapter 和 EPLB Policy：Adapter 读取统计，Policy 依次做 threshold 判断和 placement。
Provider 发布时机存在问题 当前 Runtime 在返回 maps 前先把 candidate 存进 MLB Provider；此时框架可能尚未完成权重搬运。该问题来自 MLB 自己的发布语义，与 SGLang 接入分支是否完成无关。
冷启动 · 步骤 3 是步骤 2 的展开 步骤 2 的 Glue 调用 init_by_eplb()。步骤 3 的“创建并保存 metadata”仍属于 SGLang；只把其中“普通输入算出 candidate maps”的嵌套调用替换为 Adapter 构造 PlacementRequest → EPLB Policy 生成 plan → Adapter 返回 maps。步骤 12 复用同一个 Policy。
每层只计数；整个 forward 完成后才推进时钟 TopK/dispatcher hook 在每个 MoE layer 内只更新本次 forward 的临时 physical count；执行完所有 layer 后，recorder 才 collect 并向窗口 append 一条完整记录。随后 EPLBManager 的 cadence 才前进一步。未到 every-N 就直接进入下一个 forward；到周期后 SGLang 才 dump、physical→logical、all-reduce、汇总 utilization 并 reset。黄色 Adapter 只把最终 payload 翻译成 PlacementStats。
EPLB Policy · 判断并生成布局 SGLang EPLBManager 自己维护 every-N cadence。到周期后，SGLang recorder 才执行 dump；ALL-REDUCE(SUM) 使用官方当前的 default distributed group，让各 rank 得到同一份全局 logical count，然后 reset。Adapter 将结果翻译为 PlacementStats。同一个 EPLB Policy 先判断 utilization threshold：高于阈值就结束，不高于阈值则在同一调用链中立即运行 placement 算法。
L1 算完新布局后，不能马上让 L2 切换 EPLB Policy 先算出新的 PlacementPlan，但这时权重还没有按照新布局迁移，L2 必须继续使用旧的 PlacementSnapshot。SGLang EPLBManager 随后校验并排期，ExpertLocationUpdater 完成权重搬运，再更新 metadata 并完成必要的 missing-weight recovery。全部成功后，黄色 Adapter 才从真实生效的 metadata 生成新的 PlacementSnapshot，让 L2 切换到新布局。这样 L2 看到的 placement 始终与机器上实际可用的专家权重一致。
