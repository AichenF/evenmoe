步骤 2：外层 initialize 内部调用 init_by_eplb ModelRunner.initialize() → maybe_init_expert_location_metadata() → compute_initial_expert_location_metadata() → init_by_eplb() 都属于 SGLang Glue。步骤 3 的 metadata 仍由 SGLang 创建；嵌套调用进入当前 SGLangEPLBRuntime.compute_placement()：它先把普通 tensor/scalar 包成 PlacementRequest，再调用 EPLB Planner，最后把 PlacementPlan 转回 SGLang maps。图中 Policy 前后的两个黄色框是同一个 Runtime 方法的两段转换。
Recording 入口：StatsBridge SGLang 的 TopK/DeepEP 等 backend 在每一层产生 physical count；这些 hook 先写本次 forward 的临时 gatherer。只有所有 MoE layer 完成，forward-end 才把完整 tensor 交给 SGLangStatsBridge.append_per_forward()，再 push 给 MLB Recorder。它不是每记录一层就判断 rebalance。
数据保存：EPLBRecorder 在 MLB 每个完整 forward 只复制一份 [layer, physical expert] tensor 到 MLB 的 deque，只保留最近 N 次；collect() 求和、physical→logical，并清空窗口。Recorder 只保存和整理数据，不做 placement 决策，因此用中性灰色，不归入 Policy。
另一条 Recording 路径仍存在 SGLangStatsCollector 不使用 MLB buffer，而是读取 SGLang 原生 recorder 的 dump。它与 StatsBridge 是两套互斥设计，目前代码没有选定唯一生产路径，all-reduce 语义也不一致。
第 11 步当前也被拆开 “每 N 次 forward”由 SGLang EPLBManager 触发；当前随后进入算法专用 SGLangEPLBRuntime，先 drain，并在 Runtime 内执行 threshold/skip。继续执行时仍复用 compute_placement()，所以周期路径也确实是 Adapter 构造 Request → EPLB Policy → Adapter 返回 maps。目标与它的主要差别不是有没有后置 Adapter，而是 threshold、Recorder 生命周期和 Runtime 归属。
Provider 发布时机存在问题 compute_placement() 在 Policy 返回 PlacementPlan 后，先执行 provider.update_with(plan)，然后后置 Adapter 才返回 SGLang maps。此时 SGLang 尚未完成权重搬运，因此图中红框放在 Policy 与后置 Adapter 的返回路径上。
冷启动 · 步骤 3 是步骤 2 的展开 步骤 2 的 Glue 调用 init_by_eplb()。步骤 3 的“创建并保存 metadata”仍属于 SGLang；只把其中“普通输入算出 candidate maps”的嵌套调用替换为 Adapter 构造 PlacementRequest → EPLB Policy 生成 plan → Adapter 返回 maps。步骤 12 复用同一个 Policy。
一次 forward 是整个 ModelRunner 调用，不是一个 layer with_forward_pass() 包住完整的 ModelRunner._forward_raw()。模型在其内部遍历本 rank 负责的 layer；每个 MoE layer 的 TopK/dispatcher hook 只更新同一个临时 physical-count Tensor 中自己的 layer_idx 行。循环全部结束、_forward_raw() 返回后，recorder 才 collect，并向窗口 append 一次 [layer, physical expert]。因此，对 num_hidden_layers=61 且没有 Pipeline Parallel 的 DeepSeek，一次模型 forward 跑完 61 层后才 append 一条 61 行记录；不是每层 append。开启 PP 时，每个 rank 只跑自己的 layer 区间，但仍是该 rank 整次 forward 结束后 append 一次。随后 cadence 才前进一步；到 every-N 时，SGLang 执行 dump、physical→logical、all-reduce、汇总 utilization、threshold/skip 和 reset。未跳过时，黄色 Adapter 才把最终 payload 翻译成 PlacementStats。
SGLang 判断 threshold；MLB Policy 只计算布局 SGLang EPLBManager 自己维护 every-N cadence。到周期后，SGLang recorder 执行 dump；ALL-REDUCE(SUM) 使用官方当前的 default distributed group，让各 rank 得到同一份全局 logical count。随后仍由 SGLang 根据 utilization threshold 决定是否跳过：跳过时根本不调用 MLB；未跳过时，黄色 Adapter 才把结果翻译为 PlacementStats / PlacementRequest，紫色 EPLB Policy 只负责生成 candidate PlacementPlan。
迁移完成后不主动 publish；下一 forward 按需读取 EPLB Policy 先算出新的 PlacementPlan，但这时权重还没有按照新布局迁移；在 apply 完成前，旧 metadata 仍是生效状态。SGLang EPLBManager 随后校验并排期，ExpertLocationUpdater 完成权重搬运，再提交 metadata 并完成必要的 missing-weight recovery。SGLangPlacementAdapter 持有这份 metadata 的 live reference；下一次 forward 调用 snapshot(layer_id) 时会自然读到新的 physical/logical maps，因此不需要 Step 15 再发布一份 snapshot。若某个 L2 Policy 跨 forward 缓存 placement，只需由 SGLang Glue 做版本失效，不应增加第二套 placement 状态。
