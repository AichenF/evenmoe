1. 最核心结论

这组提交最初只是把“根据负载计算专家摆放”的算法搬到 MLB；后来又把最近负载的保存、 是否需要重算的判断和结果保存一起搬了过去。算法迁移方向正确；但对 SGLang 的目标接入 应复用官方 recorder，并且不能让 MLB 在权重生效前保存第二份 placement 真值。 最后又把这些状态装进一个 SGLang 专用 runtime 并全局保存，也越过了生命周期边界。

3. 这组提交分四步搬了什么？

第一步：搬算法

把“根据专家负载和 GPU 拓扑计算新摆放”的 DeepSeek EPLB 算法放到 MLB。

判断：完全合理。这是最通用、最值得复用的部分。

第二步：搬最近负载的保存和换算

MLB 保存最近 N 次专家负载，并把物理专家数字换算成逻辑专家数字。

判断：代码本身框架中立，但不是 SGLang 目标生产路径。官方 recorder 已完整实现窗口、换算和通信，再搬一份会形成双路径。

第三步：搬“是否值得重算”的判断

SGLang 提供最近利用率，MLB 根据阈值决定是否跳过一次重新摆放。

判断：合理。这是负载均衡策略，而不是模型执行。

第四步：为 EPLB 单独造了 runtime，绕过整体 MLB 实例

负载、算法和最新摆放都被装进 SGLangEPLBRuntime，然后再用进程级全局变量保存它。

判断：不合理。架构中应该只有统一的 MoELoadBalancer 顶层实例；EPLB 只是它内部的一项能力。

5. 当前 Review 意见

意见 #1：给 SGLang 的入口太多

新旧两种负载获取方式、测试工具和替换全局对象的函数被一起公开。 应只保留 SGLang 真正需要的稳定操作。

意见 #2：不应通过 MLB 全局变量查找对象

SGLang 应在 ModelRunner 启动时创建一个 MoELoadBalancer 实例， 让 EPLBManager、TopK 等调用位置共同使用。 不需要进程级默认对象。

意见 #3：当前 EPLB runtime 绕过了整体模块入口

架构文档已经定义统一的 MoELoadBalancer。EPLB 和 Waterfill 都应该作为它内部的能力；当前代码却让 SGLangEPLBRuntime 单独拥有 EPLB 状态和算法。

Waterfill 值得复用的是由 ModelRunner 创建/注入、TopK 直接调用的生命周期模式； 但不能继续为每个 TopK 层初始化一个 WaterfillRuntime。 ModelRunner 每个模型应只创建一个 MoELoadBalancer， EPLBManager 和所有 TopK 层共同使用，通过 layer_id 区分。

意见 #4：SGLang 专用转换属于 MLB 仓库中的 Adapter

routed load 统计、EP 通信、SGLang 输入转换和 DeepEP 输出写回应留在 moe_load_balancer/adapters/sglang/，不能散落进 SGLang 主仓。

意见 #5：不能只选择一个 Router

MLB 需要支持 LPLB → Waterfill 等有顺序的组合： LPLB 的输出成为 Waterfill 的输入；两个算法共享一次通信，最后只写回一次结果。 因此顶层应管理 ordered pipeline，而不是 single-router lookup。

意见 #6：不能为每个“框架 × 算法”实现一套 Runtime

当前 SGLang 下已经分别出现 EPLB、Waterfill、LP-CF runtime。这种目录会让 多框架开发量变成 M×N。每个框架应只有一个算法无关 Adapter/Runtime， 由统一 MoELoadBalancer Orchestrator 调用 L1/L2 policies。 L1 的 candidate 不在 MLB 提前发布；L2 通过同一个 Adapter 读取 SGLang 已经生效的 metadata，不由框架手工复制一份状态。

范围说明： SGLang 接入分支仍在开发；本文不把“尚未接线”当作 MLB 组件设计缺陷。
还有一个语义冲突： 部分 MLB 注释说专家负载已经跨 GPU 汇总，但 SGLang 原始代码是在换算成逻辑负载后才汇总。 必须统一，否则会少算或重复计算。
